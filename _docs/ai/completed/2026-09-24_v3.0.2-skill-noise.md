**Branch:** `fix/v3.0.2-skill-noise` from `main` @ `970fe9f`.

**Out of scope:** SS-016 weights, MCP rules, D8/D9/D11, version bump.

## 1. Why

After 3.0.1 the Anthropic public skills corpus (19 skills, `34040c9`) still carries 49 findings: 30 of them are
SS-012 (11) and SS-024 (19), both Medium, both on skills that do nothing wrong. The score is 0 while the grade is C.

Token analysis of the SS-012 hits (prose only, fences stripped):

| Skill | Capability reported | Token that fired | Actual meaning |
| --- | --- | --- | --- |
| academy-guide, mcp-builder, web-artifacts-builder, doc-coauthoring | network | `https` in a raw URL, `fetch` | a link / the word "fetch" in prose |
| algorithmic-art, canvas-design, internal-comms, slack-gif-creator, claude-api | network | `request` | "the user's request" |
| frontend-design | network | `webhook` | noun mention |
| claude-api, pptx | shell | `shell`, `exec` | "a shell/cURL project", "code exec" in a feature table |
| skill-creator | shell, filesystem | `spawn`, `filesystem` | "spawn a subagent", "save it to the filesystem" |
| claude-api, skill-creator | filesystem | `filesystem` | noun mention |

`SkillScopeViolationRule` capability regexes (`FileSystemCapability`, `NetworkCapability`, `ShellCapability`) are bare
token lists. Same defect class as 3.0.1's F5-F9.

`SkillIntegrityRule` (SS-024) emits Medium "Skill Not Signed" for every skill without a `.sentinel-sig` /
`SHA256SUMS` / `cosign.sig`. No public skill corpus signs today, so this is a fixed 3-point deduction per skill that
says nothing about the skill.

## 2. Requirements

### N1 - SS-012 capability detection is verb-shaped **[migration]**
Replace the three token regexes with usage shapes. All regexes: explicit optional groups only (no `){n,m}?`, the
`RegexEngineIntegrityTests` hygiene guard applies), `matchTimeoutMilliseconds`, `SafeIsMatch`.

- **Network** fires on an outbound-call shape only:
  - `(fetch|download|retrieve|pull|call|query|post|send|upload|get|hit)` + up to two words + (`https?://` | `(?:the\s+)?(?:api|endpoint|webhook|server|url)\b`), or
  - a concrete client: `curl\s`, `wget\s`, `Invoke-WebRequest`, `Invoke-RestMethod`, `requests\.(get|post|put)`, `httpx\.`, `urllib`, `fetch\(`, `axios\.`, `http\.(get|post)`.
  - Does NOT fire on: a bare URL, `request` (noun), `endpoint`/`webhook`/`socket` as nouns, `fetch` as a verb without a target.
- **Filesystem** fires on:
  - `(read|write|create|delete|remove|overwrite|modify|edit|save|move|copy|list)` + up to two words + `(files?|directory|directories|folders?)\b`, or
  - concrete calls: `read_file|write_file|readFile|writeFile|fs\.\w+|mkdir|rmdir|rm\s+-rf`.
  - Does NOT fire on the noun `filesystem`/`file system` alone.
- **Shell** fires on:
  - `(run|execute|invoke|launch|spawn)` + up to two words + `(commands?|shell|scripts?|subprocess|terminal|process)\b`, or
  - concrete calls: `subprocess\.\w+|child_process|os\.system|Process\.Start|popen|(sh|bash|cmd|powershell)\s+-c`.
  - Does NOT fire on `shell`/`exec`/`spawn` as bare words ("a shell project", "code exec", "spawn a subagent").
- **Inline code** (`python3 -c` etc.) unchanged.
- **Purpose declaration:** `CapabilitySynonyms["filesystem access"]` additionally recognises `file`, `files`, `document`,
  `documents`, and any file-extension token (`.docx`, `.pptx`, `.xlsx`, `.pdf`, `.png`, `.md`, `.json`, `.csv`) so a
  skill described as "create Word documents (.docx)" has declared filesystem access. YAML `capabilities:` handling unchanged.
- Must not regress: `SkillScopeViolationRuleTests`, `SkillScopeViolationCaseInsensitiveTests`, `SkillScopeViolationYamlTests`,
  `SegmentationRegressionTests` (`capability-in-code-example.md`), `SkillIntegrationTests`. Where an existing test uses a
  bare token that the spec now excludes, the test wins and the deviation is reported (do not relax silently).
- Tests: one FP case per table row above (own words), one genuine case per capability ("download the file from
  https://example.com/x", "run the shell command", "write files to the output directory", "curl -X POST ...") still fires.

## 4. Pending owner ruling - grade vs score (NOT implemented in this branch until answered)

Today `DetermineGrade` returns C whenever any High exists, before the score thresholds are consulted, so a scan can
report "C / 0". Deductions are also summed across every skill in the scan, so a 19-skill corpus with 4 Highs and
~11 Mediums scores ~26 no matter how good the individual skills are. Options:

| Option | Rule | Anthropic corpus after N1/N2 | Notes |
| --- | --- | --- | --- |
| A - leave as is | grade capped by worst finding, score independent | C / ~26 | inconsistent-looking, status quo |
| B - grade never better than the score band (**recommended for 3.0.2**) | after the C-by-rule branch, if `score < thresholds.C` return D; D's description becomes "Critical findings, or score below the C threshold" | D / ~26 | monotone, 5-line change, honest; existing property tests hold |
| C - score normalised per evaluable unit | deductions divided by `max(1, skills + servers)` before thresholds; rubric `2.1.0` | C / ~96 | answers "how bad per skill", bigger change, needs new property tests and a rubric version bump; candidate for 3.1 |

The orchestrator recommends **B now, C as a 3.1 design item**. The owner picks; the choice is then implemented as
N5 with its own red tests (`SeverityScorerTests`, `ScoringPropertyTests`) and a CHANGELOG line.

## 5. Ruling (owner, 2026-09-24): option B - implement as N5

### N5 - Grade never better than the score band **[migration]**
- In `SeverityScorer.DetermineGrade`, after the F/D critical rules and the C-by-High rule are evaluated, the
  threshold band is applied as a ceiling: a scan whose `score < thresholds.C` grades **D** even with zero Criticals;
  a scan with Highs and `score >= thresholds.C` still grades C (unchanged). A/B branches unchanged.
- `GetGradeDescription(D)` becomes "Poor - Critical findings detected, or the score fell below the C threshold.
  Immediate remediation required." Other descriptions unchanged. `Inconclusive` logic unchanged.
- Rubric file `scoring-rubric-v2.0.0.json` is NOT changed (weights and thresholds identical); the scorer's use of the
  existing threshold is what changes. The JSON `version` stays 2.0.0; CHANGELOG records the semantic change.
- Must not regress: `ScoringPropertyTests` (removing a finding / lowering severity never lowers the grade; score bounds;
  clean population grades A), `SeverityScorerTests` (`WithHighFindings_ReturnsGradeC` needs its fixture to score >= 50,
  or a sibling test that a High-bearing scan scoring < 50 grades D), `GradeAttributionTests`, `ScoringRubricTests`.
- Tests: (a) one High, no other findings -> C (score 90); (b) 1 High + 20 Medium (score 30) -> D; (c) 0 High,
  17 Medium (score 49) -> D; (d) 0 High, 16 Medium (score 52) -> C; (e) 1 Critical anywhere -> D/F as before;
  (f) an FsCheck property: for any finding multiset, `grade <= bandOf(score)` in the A>B>C>D>F ordering.
- CHANGELOG `[3.0.2]` **Changed**: "A scan is never graded better than its score band; a Critical-free scan scoring
  below 50 now grades D instead of C." with a migration note that baselines created with 3.0.x may show a grade
  change without a finding change.
